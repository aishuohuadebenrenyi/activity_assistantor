## 一、主办方与用户交互场景及逻辑流程

### 1.1 角色定义与权限矩阵

| 角色 | 平台 | 核心能力 | 权限范围 |
|------|------|----------|----------|
| **主办方** | iOS/Android App | 创建活动、编辑活动、删除活动、签到管理、数据导出、分享推广 | 完全管理权限 |
| **参与者** | 微信小程序 | 浏览活动、报名活动、查看电子票、签到、取消报名 | 仅自身报名记录 |
| **游客** | 全平台 | 浏览活动列表、查看活动详情 | 无写权限 |

### 1.3 平台差异化策略（设计决策）

> **重要说明**：App端不实现报名功能是产品设计决策，而非功能缺失。
> - 主办方使用 App 进行活动管理和签到核销
> - 参与者使用微信小程序进行报名和查看票据
> - 这种分工符合实际使用场景：主办方需要强大的管理工具，参与者需要便捷的报名入口

| 功能模块 | iOS/Android App | 微信小程序 | 设计原因 |
|----------|-----------------|------------|----------|
| 创建活动 | ✅ TabBar入口 | ❌ 不可用 | 主办方专属功能 |
| 编辑活动 | ✅ 详情页编辑 | ❌ 不可用 | 主办方专属功能 |
| 签到管理 | ✅ 扫码+手动 | ❌ 不可用 | 主办方专属功能 |
| 浏览活动 | ✅ 首页列表 | ✅ 分享进入 | 两个入口 |
| 报名活动 | ❌ 设计决策不实现 | ✅ 底部按钮 | 参与者使用小程序 |
| 我的报名 | ✅ Profile入口 | ✅ TabBar首页 | 不同导航结构 |
| 举报功能 | ✅ 通用入口 | ✅ 详情页入口 | 合规要求 |

### 4.2 签到验证机制

```
┌─────────────────────────────────────────────────────────────────┐
│                        签到验证流程                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │ 签到码解析:                                              │   │
│  │                                                          │   │
│  │  原始格式:                                               │   │
│  │  CHECKIN:<activity_id>:<registration_id>:<timestamp>:<signature>│
│  │                                                          │   │
│  │  解析步骤:                                               │   │
│  │  1. Base64 解码                                         │   │
│  │  2. 按 ':' 分割                                         │   │
│  │  3. 校验 parts[0] == 'CHECKIN'                          │   │
│  │  4. 提取 activity_id, registration_id, timestamp        │   │
│  │  5. 验证签名 (可选)                                      │   │
│  │                                                          │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │ 验证规则:                                                │   │
│  │                                                          │   │
│  │  1. 权限验证                                             │   │
│  │     if (request.user.id != activity.user_id)            │   │
│  │       → 403 只有组织者可签到                             │   │
│  │                                                          │   │
│  │  2. 活动匹配验证                                         │   │
│  │     if (qr_activity_id != url_activity_id)              │   │
│  │       → 400 非本活动的签到码                             │   │
│  │                                                          │   │
│  │  3. 报名记录验证                                         │   │
│  │     if (!registration || registration.activity_id != id)│   │
│  │       → 404 报名记录不存在                               │   │
│  │                                                          │   │
│  │  4. 重复签到检查                                         │   │
│  │     if (registration.checkin_record != null)            │   │
│  │       → 200 已签到提示 (不报错)                          │   │
│  │                                                          │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │ 签到记录创建:                                            │   │
│  │                                                          │   │
│  │  CheckinRecord {                                         │   │
│  │    id: auto_increment,                                   │   │
│  │    registration_id: 报名记录ID (unique),                 │   │
│  │    activity_id: 活动ID,                                  │   │
│  │    checkin_time: 签到时间,                               │   │
│  │    device_info: 设备信息 (预留防作弊)                     │   │
│  │  }                                                       │   │
│  │                                                          │   │
│  └─────────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────┘
```

## 总结

本报告对 Zentro 项目进行了全面的功能与交互逻辑梳理，涵盖了：

1. **主办方与用户交互场景**：明确了双平台差异化策略，主办方使用 App 管理活动，参与者通过小程序报名签到。App端不实现报名功能是产品设计决策。

2. **活动管理业务链路**：从创建、编辑、分享到删除的完整流程，包含离线支持和内容安全审核。

3. **报名业务链路**：从浏览、报名、获取票据到取消报名的完整流程（小程序端），包含多重校验机制。

4. **签到流程**：扫码签到和手动签到两种方式，包含验证机制和异常处理。

5. **签到管理功能**：实时统计、搜索筛选、数据导出等管理能力。

6. **问题与风险分析**：识别了功能缺失、流程断点、逻辑矛盾、安全风险等问题。

7. **上线待办事项**：从功能完整性、流程顺畅性、用户体验、技术实现、合规审核五个维度列出了详细的工作清单。

**建议优先处理的问题**：
- 🔴 浏览量防刷机制（数据可信度）
- 🔴 签到码安全性增强（防止作弊）
- 🟠 消息通知系统（用户体验）
- 🟠 测试覆盖（质量保障）
